# Context harness evaluation

The [runtime contract](../../features/context-harness.md) covers the implemented tools, ownership rules and deterministic verification. The remaining decision is whether any experimental feature should become a default. No hosted-model comparison has established that.

## Why these mechanisms

- Improve acquisition before compaction. Existing search and range tools can bound a read; work notes cannot recover original bytes that a shell preview has already discarded.
- Prefer one long empty poll for ordinary jobs. Register completion only when a live turn explicitly needs the result. A terminal event is evidence, not permission to start another turn.
- Use a fresh explorer for an independent question, not a directed lookup. A narrower parent transcript can still mean more aggregate inference or worse coverage.

## Remaining work

1. Select the provider, model, task revisions and run budget for the [controlled comparisons](evaluation_plan.md). Capture the effective child provider, model and overlays. Score known answers, unsupported conclusions and stale references separately from token counts.
2. Keep structured exposure, retention and scheduling opt-in pending those results. Do not infer lower cost, better answers or fewer compactions from scripted request counts.
3. Before extending platform support, validate the actual search launcher and pipe/PTY drainage on that platform, including a descendant holding a descriptor. Legacy Windows restricted-token capture and streamed restricted-token search are not supported; no portable guarantee follows from the macOS probe.
